# ADR-012: The eval service runs from CI and the laptop; its nightly Lambda moves to M05

**Status:** Accepted
**Date:** 2026-08-08
**Milestone:** M03

## Context

ARCHITECTURE.md §3 describes the eval service as running "in CI + nightly
Lambda". M03 builds the eval service; the natural reading is that M03 also
deploys the Lambda.

It should not, because in M03 the Lambda has nowhere to put its output and
nobody to tell. The dashboard that would read a nightly score trend is M05's
(`dashboard-as-code: eval trend`), and the workflow that would schedule it is
M05's (`nightly-eval.yml`). Deploying the function now means shipping a Lambda,
an execution role, a log group, and a schedule rule whose entire observable
behaviour is writing rows nobody reads until two milestones later — and whose
failures nobody would notice, because no alarm exists yet either.

The eval harness is also already where it needs to be. It is pure over a
`Caller`, so the same code runs from a developer's shell under `make eval`,
from CI under M05's workflow, and from a Lambda whenever one exists. Nothing
about deferring the function changes the code that would run inside it.

Standing rule 8 is the deciding force: a component that works and is shaped
correctly is done, and polish is M07's job.

## Decision

**`AgentPave-Eval-dev` contains exactly one resource: the DynamoDB baseline
table. No Lambda, no execution role, no schedule. Adding compute to this stack
before M05 is forbidden without a superseding ADR.**

`platform/infra/tests/test_eval_stack.py` asserts the absence — the stack must
synthesise zero `AWS::IAM::Role` and zero `AWS::Lambda::Function` resources —
so the constraint is enforced rather than remembered.

The eval service reaches Bedrock only through the gateway, which is why this
stack needs no role of its own: the credentials that run `make eval` are the
operator's, and the gateway holds the only `bedrock:InvokeModel` in the
platform (ARCHITECTURE.md invariant 1). That property is asserted negatively in
the same test file.

Constraints carried forward, to be checked at M05 review:

- [ ] `nightly-eval.yml` invokes `pave eval --diff --save-baseline`, not a
      reimplementation of the harness
- [ ] The nightly runner, wherever it lands, holds zero `bedrock:*` and calls
      the gateway like every other caller
- [ ] The eval-trend dashboard reads the baseline table this stack creates,
      rather than a second store

## Consequences

**Easier.** M03's deployed gate is `make eval` from a shell, watched by a
human — which is what a milestone review needs. The stack is one table, so
`make deploy-dev` stays fast and `make destroy-dev` leaves nothing behind. No
role exists that could accidentally acquire Bedrock access.

**Worse.** There is no unattended eval until M05. Nothing catches a quality
regression introduced by a model-side change between milestone reviews, and
the baseline table will hold only the handful of rows a human generated by
running the gate — so M05's first trend chart starts nearly empty and the
diff has little history to be interesting against.

**Forecloses nothing structurally**, which is the point: the Lambda's absence
is a packaging decision, not a design one. Adding it in M05 is a stack edit
plus a workflow file, with no change to the harness, the dataset, or the
baseline schema. If that turns out to be false at M05, this ADR was wrong and
gets superseded rather than quietly ignored.
